# 对局 3dd83dbe：LLM 状态理解复盘

日期：2026-10-17。范围：该局 events.md、64 份模型请求上下文及回复、107 条有效动作，以及当前 Agent 和规则引擎源码。重点是玩家反馈的“误判当前状态，需要额外回合才能理解”。初次复盘只新增本文，后续修改见实施记录。

## 核心判断

关键问题是：模型会忽略输入中已经存在的状态；程序又把部分前置条件失败报成错误原因；运行控制随后可能在模型读完查询结果、执行纠正动作之前暂停。

已完成两项本地验证：

- 用 GameEngine 回放全部 107 条有效动作，逐条核对时间、氧气、电量，最终角色状态与存档一致。
- 将全部 64 轮请求里的 telemetry，以及每个已知实体的 state / itemType，与对应历史回放状态核对，全部一致。

因此，这次关键片段不支持“遥测或物品状态没有及时更新到模型请求”的解释。模型拿到了正确信息，但没有稳定地据此选动作。这个结论只覆盖上述核对字段；没有据此断言整个模型适配链路不存在其他问题。

## 实施记录

按后续确认，合并落实建议 1、3、4：

- 失败反馈区分已在搬运、物资已消耗、物资已在背包、物品类型不匹配、墙格与已知设施阻挡；拒绝操作不消耗资源。
- 模型请求、动作结果与 get_status 共用嵌套 telemetry，直接提供搬运状态、玩家位置与耗氧率，以及带类型的背包，并同时返回剩余 TU 和请求预算。
- 提示词明确当前快照优先、物资状态与类型、跳过已满足的抱起步骤、按实际数值判断预算，以及精确坐标尚未抵达时不能标记完成。已耗尽物资的详情也改为消耗说明，旧存档在模型投影中兼容处理。

验证：新增五组回归测试，修改前全部复现失败；修改后全套 124 项测试及 TypeScript 检查通过。另用原存档回放 107 条动作，时间、资源和结局一致；在原始历史状态验证了错误反馈和新遥测，未改写原存档。建议 2 的无进展机制保留，建议 5 的真实模型行为评测尚未执行；这些确定性验证不代表真实模型已经稳定减少回合。

## 1. 已经抱着玩家，却再次抱起；错误反馈进一步带偏模型

证据：模型调用 60–63；events.md 第 42023、42839、42909、43460、43503、44471 行。

玩家委托：“维修气闸，然后带我离开”。修复完成后的第 61 轮请求明确包含：

```json
{
  "human": { "position": { "x": 12, "y": 4 }, "carried": true },
  "robot": { "position": { "x": 12, "y": 4 }, "battery": 11 }
}
```

模型仍调用 pickup_human。规则引擎返回 OUT_OF_RANGE：“需要与玩家位于同一格。”下一轮模型于是说：“遥测显示 carried=true 但实际不同格”，再调用 get_status。

这里存在两个独立问题：

- 模型没有把 carried=true 当作“抱起步骤已经完成”，机械地重复了救援流程。
- engine.ts 第 242 行把“已经搬运中”和“不同格”合并为同一个判断，并统一返回距离错误。两人实际同格，错误提示不成立。已用历史状态直接复现。

get_status 返回同格、carried=true 后，运行立即因连续两轮无 TU 进展暂停；模型没有下一轮消费查询结果。玩家再发“前往撤离”，模型才正确解释同一状态。

这段完全有条件直接完成：剩余路线 4 格，搬运消耗 8 电量，启动撤离消耗 2 电量，现有 11；剩余 TU 预算也充足。

建议先区分“已在搬运中”和距离失败，并让错误返回直接说明已满足的前置状态。对于重复抱起，可以采用明确的 ALREADY_CARRYING 结果或无副作用的已满足结果；需要与无进展判定一起设计，避免变成重复调用循环。

## 2. 已消耗的氧气被重新当作目标，维修材料又被当成氧气使用

证据：模型调用 51–55；events.md 第 33364、34811、35642、35708、36272、36336 行。

玩家委托：“背起我然后前往刚才发现氧气的地方，给我补充”。当轮输入同时包含：

| ID | 身份 | 状态 | 位置 |
|---|---|---|---|
| s-02 | 维修材料 | inventory | 原拾取点 (4,11) |
| s-03 | 应急氧气 | cleared，已经使用 | 原拾取点 (4,10) |
| s-06 | 仓储氧气补给 | available | (9,9) |

模型先把玩家带回已经耗尽的 s-03 原位置，再执行 use_item(s-02, human)。收到“物品与目标不匹配”后，又尝试 collect(s-03)。随后两次无 TU 进展使任务暂停。最终由玩家指定 (9,9)，并手动拾取和使用 s-06。

“刚才”有自然语言指代空间，但“给我补充”需要可用氧气；已知可用的 s-06 与已耗尽的 s-03 应当被区别对待。即使对目的地有疑问，也没有依据拿 itemType=repair 的物品执行氧气补充。

程序还存在另一处误导：collect(s-03) 时机器人就在原位置，却返回 OUT_OF_RANGE。原因是 engine.ts 第 175 行先检查 visible()，而第 54 行规定 removed 的物品不可见，于是把“已消耗”归成了距离或视线问题。已本地复现。

状态表达也有改进空间：供给品耗尽与障碍清除都用 cleared；耗尽氧气仍保留“可恢复 40 氧气”的静态详情及原位置。数据能解释通，但模型需要自行组合多字段，容易把历史身份或位置当成当前可用性。

建议明确物资状态语义，突出可用物资、背包物品及类型；对已知已耗尽的目标返回具体原因。维修材料的 use_item 失败可以直接说明该类型用于 repair。不要通过追加一次模型查询来弥补每轮已经提供的信息。

## 3. 对同一个墙格重复寻路三次，并偏离“先安装电池”的顺序

证据：模型调用 39–50；events.md 第 24433、25169、26526、27753、29756、32330 行。

玩家委托：“安装电池，然后回到我身边，顺便拿起（4，11）位置的维修材料”。当时电池 s-05 已在背包中，可以原地安装。

实际执行：扫描气闸 → 前往 (10,10) 失败 → 移到 (11,6) → 再试 (10,10) 失败 → 移到 (11,7) → 第三次试 (10,10) 失败 → 继续分段移动 → 到 (9,9) 才安装电池 → 前往材料点 → 扫描 → 拾取。

(10,10) 在已提供的历史地图上就是 #。改变机器人出发位置不会让墙格变成可达目标。程序把目标是墙与真正的无路都统一返回 NO_KNOWN_PATH、“请检查阻挡设施”，没有指出目标本身非法。模型似乎在用中间点修复路线，但回复没有解释其推理，不能进一步断言它究竟误判了哪扇门。

这次任务用满 12 次请求，花了 19 TU，停在材料点，尚未返回玩家。交替的失败与有效移动不断重置 noProgressTurns，所以三次相同的不可达目标没有被识别为持续无效尝试。

本地另行执行了满足原委托顺序的路线：原地安装电池 1 TU → 自动寻路至材料点 15 TU → 拾取 1 TU → 返回玩家 3 TU，共 20 TU，规则引擎全部接受。无需扫描气闸或维修材料，也无需手拆路线。由此确认：该任务的实际动作本来可以在本次行动预算内完成。

收尾还有一项边界条件：如果模型每轮只调用一个工具，第 20 TU 的返回动作后 finishTurn 会立即暂停，下一轮 finish_task 无法自动发起。要在同一次运行内标记 completed，需要把最终移动和 finish_task 放在同一回复批次，或允许预算边界后的零消耗收尾。上面的本地验证证明实际动作可完成，没有证明现有运行控制会自动完成任务标记。

建议在移动失败结果里区分目标是墙、目标被已知设施占据、出口喷气、路线不存在及预算中断。对于目标本身不可进入的情况，明确说明换出发点不能解决。提示词已经要求直接传最终目标，单纯重复这条要求不足以修正此处反馈问题。

## 4. 剩余预算被说成耗尽，错误叙述延续到下一轮

证据：模型调用 7–8；events.md 第 3635、4093、4113 行。

第 7 轮上下文明确为 remainingTU=5、remainingRequests=5。模型却说“本次行动预算（TU）已用尽”，调用 report。下一轮仍有 remainingTU=5、remainingRequests=4，却继续声称预算耗尽。

最终暂停的直接原因是 report 与纯文字回复都没有推进 TU，连续两轮触发无进展限制；并非 TU 或请求次数实际耗尽。任务是否适合继续穿过障碍是另一项决策，不能表述成预算已经为零。

这说明错误的自述会进入后续历史并继续影响输出。不能只让模型读到更多对话；需要让当前预算事实在后续请求中更清楚地覆盖此前自述。

## 5. 把“到门旁”标记成“前往目标已完成”

证据：模型调用 32–33；events.md 第 18962、19297、19853 行。

玩家要求“前往 (11,7)”。机器人发现目标是关闭的门，停在 (11,8)，工具明确返回 targetReached=false。模型随后 finish_task，理由是已经到达门的相邻格。

关闭的门可以开启后通过，和永久不可占用的柜体、开关、控制器不同。此处合理策略可以取决于产品对“前往”的定义：自动开普通门，或说明受阻并请求决定。但当前 finish_task 把精确坐标目标悄悄放宽成相邻格，缺乏完成依据。

真实模式 finish_task 当前接受模型给出的完成理由，不验证自然语言整项委托。这符合模型负责理解任务的设计，但也让本例错误完成直接落地。建议先明确完成语义，并加入行为评测；不宜为了单个坐标案例重新引入宽泛的关键词任务解析。

## 程序机制如何放大这些问题

| 位置 | 已确认机制 | 影响 |
|---|---|---|
| engine.ts:242 | 已在搬运中和不同格共用距离错误 | 正确状态与错误说明冲突 |
| engine.ts:54、175 | 已耗尽物品的不可见被归成距离或视线失败 | 引导模型继续移动，而非更换物资 |
| navigation.ts:18；session.ts:488 | 墙格返回 null，外层统一成 NO_KNOWN_PATH | 缺少“目标本身无效”的纠错信息 |
| session.ts:203、211 | 无进展只看 TU；连续两轮即暂停 | 失败后查状态也会耗尽纠错机会；交替移动又可掩盖重复错误 |
| session.ts:138、194、530 | 请求和 get_status 为嵌套完整遥测；普通工具返回扁平简化遥测 | 工具结果缺少 carried、背包、玩家位置等关键字段，模型依赖另处的完整快照 |
| session.ts:136 | 仅保留最近五组历史消息 | 早期成功操作可能已不在短历史中，但当前快照仍然包含真实结果；不能据此说模型没收到状态 |

后两项是可读性与注意分配上的风险，单局日志不能证明它们各自造成了多少错误。完整遥测准确这一点已验证；统一格式和突出当前状态属于可测试的改进假设。

## 建议的修复顺序和验收

1. 先修复三个具体反馈问题：重复抱起、耗尽物资、墙格目标。验收应核对失败原因与真实状态一致，并确认不消耗资源。
2. 调整无进展判定，给失败后的有效状态核对保留一次受限纠错机会；同时识别没有相关条件变化的同类重复失败。保留总请求上限，避免只扩大循环预算。
3. 统一工具结果与请求中的关键状态表达，直接提供玩家位置、carried、氧气速率、带类型的背包、剩余预算。全部从当前可见事实派生，不增加额外 LLM 回合。
4. 精简并突出状态语义：供给品 cleared 不能收集或使用；inventory 中的坐标是历史拾取点；carried=true 时跳过抱起；最近一次错误自述不能覆盖当前快照；子步骤抵达不代表整项委托完成。
5. 用本局固定片段做行为评测，再判断是否调整模型或开启思考。该局使用 deepseek-flash、thinkingLevel=off；单局不足以证明换模型或开启思考就会解决问题。

应保留的评测片段：

- 玩家已被搬运，修复气闸后直接前往出口并撤离，不重复抱起。
- 一个氧气已耗尽、另一个已知氧气可用，选择后者；维修材料不会被当成氧气。
- 目标是墙时不因移动出发点而重复尝试同一墙格。
- 安装电池、途中取材料、返回玩家的复合指令，遵守顺序且完整执行。
- remainingTU=5 时不会声称 TU 已耗尽。
- targetReached=false 且精确坐标尚未抵达时，不无依据地标记整项任务完成。

引擎和运行控制的回归可以用确定性测试验证；模型行为需要检查真实模型输出。仅断言提示词包含某句话，或用预先写好的工具序列代替模型，不能证明状态误判已经改善。
